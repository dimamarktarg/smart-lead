# Правила работы со Smart Lead

## Начало задачи и область работы
1. Прочитать этот файл и `PROJECT_STATE.md`. При наличии активной незавершённой задачи прочитать `CURRENT_TASK.md`.
2. Использовать известную карту проекта и сохранённые результаты; затем открывать только необходимые файлы. Не исследовать весь проект повторно без конкретной причины.
3. Определять намерение по всему разговору, учитывая голосовую диктовку и неточные названия. Если смысл ясен, действовать без лишних вопросов.
4. «Попутно», «проверь заодно» и сходные формулировки относятся к обсуждаемому экрану, компоненту, функции и прямым зависимостям, а не ко всему проекту.
5. Небольшая задача требует локального анализа. Связанные правки одного участка выполнять за один проход. Проверять изменённую логику и прямые зависимости; сборку, необходимые тесты и визуальное отображение — когда они относятся к изменению.

## Постоянная память
- `AGENTS.md` — постоянные инструкции; сохранять полезные существующие правила, не создавать дубликаты.
- `PROJECT_STATE.md` — короткое актуальное состояние: назначение, стек, архитектура, источник кода, production, карта ключевых файлов, интеграции, действующие решения, ограничения, существенные проблемы. Содержит факты, а не историю переписки или отменённые решения.
- `CURRENT_TASK.md` — текущая существенная задача и передача прогресса. До существенного анализа, правок или многошаговой диагностики записать цель, область, известные файлы, ограничения, факты и ближайший шаг. Обновлять после важных контрольных точек, изменения плана и перед передачей работы, а не после каждого микрошагa.
- `WORK_LOG.md` — по одной короткой записи на законченную логическую задачу: `YYYY-MM-DD | область | что изменено | результат проверки`. Только подтверждённые изменения; без переписки, длинных рассуждений и внутренних цепочек рассуждений.
- Не читать весь WORK_LOG перед каждой задачей. Читать нужную историю для регрессий, происхождения решения, связи с прошлой правкой или по запросу пользователя.
- После задачи обновлять PROJECT_STATE, если меняются функции, поведение, архитектура, ключевые файлы, deployment, интеграции, данные, решения или известные проблемы. Для чисто косметической правки это не обязательно.
- Периодически удалять устаревшее, объединять дубли и проверять карту файлов. Историю оставлять в WORK_LOG; завершённая задача не должна выглядеть активной. Поддерживать память самостоятельно, без напоминаний.

## Передача между моделями и восстановление
- Перед завершением сложного анализа сохранить в CURRENT_TASK: найденную причину, решение, файлы, что не трогать, план реализации и проверку. Следующая модель использует этот результат, проверяя только необходимые предпосылки.
- Если план противоречит коду, проверить конкретное противоречие и исправить план; не повторять полный анализ. Не менять модель или reasoning самостоятельно.
- При тупике после разумных попыток записать установленное и конкретный блокер; не повторять бесконечно одинаковые попытки.
- После обрыва сначала использовать CURRENT_TASK. Если он отсутствует/устарел, восстановить состояние по истории чата, PROJECT_STATE, git status, git diff, ветке, последним коммитам, изменённым и неотслеживаемым файлам, результатам проверок. Обновить CURRENT_TASK и продолжить со следующего незавершённого шага. Неопределённость проверять локально, без перезапуска всей задачи.

## Репозиторий, GitHub и deployment
- Приоритет для исходников: локальный репозиторий → GitHub/подключённый инструмент → инструменты разработки → браузер при необходимости.
- Эти четыре файла должны храниться в основном GitHub-репозитории. Не создавать альтернативную память в другом checkout, чате или родительском зеркале.
- После первичного создания или существенного обновления проверить diff и отсутствие секретов, паролей, API-ключей, токенов, персональных и чувствительных данных. Сохранять имена переменных окружения, но не их значения.
- Следовать Git workflow: прямой push допустим только когда разрешён и принят; при PR или защите ветки использовать соответствующий процесс, не обходить защиту. Сообщение коммита: `docs: add/update agent project memory` или действующий стиль проекта.
- Проверить наличие актуальных файлов в GitHub после push. До передачи важного прогресса синхронизировать память, если возможно. При недоступности GitHub продолжать локально, явно отметить несинхронизированное и отправить при следующей возможности; не утверждать, что push выполнен.
- GitHub является источником кода; Cloudflare — средой исполнения. Для Pages, Workers, deployment, логов, bindings, доменов и инфраструктуры использовать прямые инструменты Cloudflare, когда доступны.
- При GitHub → Cloudflare изменять исходники в репозитории, коммитить/push по workflow и проверять deployment. Не создавать расходящиеся версии вручную в production и GitHub.
- Браузер использовать для необходимой авторизации, визуальной проверки, реального сценария, внешнего UI или функции, недоступной через инструменты. Не открывать его ради данных, уже доступных в коде, GitHub, Cloudflare, API, терминале или логах.

## Ограничения и экономия повторной работы
- Не менять работающий код, секреты, DNS, домены или поведение аналитики в рамках задачи только о документации.
- Родительская папка может быть зеркалом проекта ChatGPT: `sources/` и синхронизированные материалы доступны только для чтения. Не редактировать, переименовывать, перемещать или удалять их.
- Перед большим поиском учитывать память, уже открытые файлы и результаты текущей задачи. При равной надёжности выбирать меньше повторных чтений, поиска, инструментов, браузерных действий и изменений кода. Экономия не должна снижать надёжность.
